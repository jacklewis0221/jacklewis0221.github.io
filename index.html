Common Service Tool: one service workflow across machine generations.

The problem

A technician should be able to connect to a machine, read sensor values and faults, and update what the machine supports, including controller firmware and applications, onboard displays, and remote-control units, without a different tool for every machine family and controller generation. A common interface still doesn’t mean one update path for every target.

Where my work ended and the team’s began

Mine: initial commits and development infrastructure, CAN/J1939 memory-access operations, the CI and automated-test foundation, the QML reuse investigation with Qt support, architecture documentation, and the Qt Working Group.

Team and inherited: the reflash redesign, the model-based hardware framework, update and recovery paths, and dealership machine logging.

Field note · public SAE J1939-73 concepts

DM1 and DM2 answer different questions.

DM1 · PGN 65226 · 0xFECA

What is wrong right now?

Active diagnostic trouble codes, broadcast periodically, commonly once a second, with lamp status for the malfunction indicator, red stop, amber warning, and protect lamps.

DM2 · PGN 65227 · 0xFECB

What was wrong before?

Previously active trouble codes, sent when a service tool requests them. Each carries an occurrence count, which is a count, not a timestamp or a dated history.

Build a trouble code

Four DTC bytes, as they appear in a DM1 or DM2 payload

6E 00 00 03

  • SPN · 19 bits
  • FMI · 5 bits
  • CM · 1 bit
  • OC · 7 bits

What I carry to the next system

  1. 01

    Count the full cost of reuse.

    Reusing a J1939 stack or an existing QML front end saves implementation, not effort. Learning the code, adapting its assumptions, integrating, verifying, and maintaining it still land on the team, so budget for them up front.

  2. 02

    Match verification to release risk.

    A passing build doesn’t prove every machine target or update path works. Ask what evidence a change needs given how it will be used, what a failure would cost, and whether you could detect and recover from one.

  3. 03

    Show only the state you can prove.

    If a connection drops in the middle of an update, the outcome is unknown: not success, not bricked. Service software should report what it has verified, check the target through supported means, and route to the right recovery path.

  4. 04

    Make context portable.

    On a distributed team with different hardware backgrounds, a shared glossary, readable diagrams, expected-versus-observed notes, and a named owner for the next step turn one person’s knowledge into the team’s.
